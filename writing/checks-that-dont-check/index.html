Your green build doesn't prove the fix is still there

Assert the use, never the declaration. I put forty-two fixed defects back into the tree, and thirty-three of the checks certifying them closed stayed green.

September 2026

I have a script whose only job is to assert that every finding from a security review is actually closed. Not closed according to a spreadsheet. Closed according to a property of the source tree that is false while the defect is present and true once it is gone.

It reported 48 of 48.

That number is worth exactly as much as the checks behind it, and I had never tested the checks. A passing check tells you it passed. It does not tell you it would have failed.

So I went and found out. For each closed finding I put the original defect back into the tree and re-ran the script.

Thirty-three of forty-two entries stayed green with the defect back in place.

That is not a slip in a few entries. That is most of the gate.

What it did not notice

A hash function computing the wrong version. An empty screener set admitting everything. A veto window deleted so account recovery executes instantly. A bounds check bypassed at both of its call sites. Private content relaying again. An enum variant renamed back to the name the finding was written about.

Every one of those is a real defect that had been found, fixed, and then certified as fixed by a check that was not looking at it.

Four ways a check can be true while the bug is present

I knew about three. The script's own header listed them, because it had shipped all three at once.

Wrong artefact. The defect lived in a documentation file and the entry asserted something about a source file. Nine entries did this. A check reads the file the finding names, or it is measuring something else.

A needle that occurs anyway. Asserting that the string device_id appears in a document is true eleven times over for unrelated reasons. Delete the entire schema the finding is about and the check still passes.

A comment instead of the code. A comment reading NOT with_capacity(seq) survives the exact reversion it describes. So does a symbol named after the bug. Asserting that HeadBehindConfirmed appears asserts that the defect is present, not that it is gone.

The fourth is the one the audit found, and it accounted for fifteen of the thirty-three.

A declaration, where the defect lives in the use.

An enum variant declared while the arm that returns it is deleted. A struct field and its accessors surviving while the line that populates it goes. A function whose own body satisfies the check while both call sites stop calling it. A heading matching while the paragraph under it is gutted. A value still computed while nothing consumes it.

And the one I would put on a poster: a test whose name still matched, while its body had been replaced with if true { return; }.

Assert the use, never the declaration.

This is not really a testing problem

The shape generalizes well past test suites, which is why it seemed worth writing down.

Anything that certifies something else has this failure mode. A compliance check that greps for the existence of a policy file. A lint rule that fires on a pattern the real bug does not happen to use. A dashboard panel that goes green because the query returned rows. A deploy gate that confirms the service is listening. Each one measures a proxy for the property it cares about, and the proxy and the property agree right up until the moment they stop.

The tell is which direction the assertion runs. A check that confirms the good state is a claim that can quietly stop being true, because the thing that made it true has moved. A check written to fail when the bad state appears has to go and find the bad state. Only one of those two survives a refactor with its meaning intact.

The part where I was wrong

The audit flagged three checks that run before a signature is verified, against a module header saying that nothing is reported about attacker-controlled fields until the signature has been checked.

The code was right and the header was wrong. The conformance vector says so in its own note: the size bound is checked before the signature because it needs no key. The header forbade the thing the vectors require. A second implementation written from that prose would return a signature error where this one returns a size error, which is the precise disagreement that module exists to prevent.

So I fixed the header.

An audit that only ever confirms your suspicions is running the same failure as the gate it was sent to audit.

What it cost

Every closure resting only on that gate was unverified for as long as it stood, which is the whole period it was reporting a clean sweep. The findings that had been checked by hand against a property that fails when the fix is reverted still stand. Nothing else did.

Thirty of the thirty-three are repaired now. Each was verified by putting back the exact defect the audit demonstrated surviving, confirming the check fails on it, and confirming it passes without it. Three are not repaired, and they are named with their reasons rather than quietly counted as done.

Thirty-nine of forty-two sound is a worse headline than forty-eight of forty-eight. It is also the first of the two that was ever true.

The point

The best sentence in that script is one it says about itself:

A rule this file states about itself is worth no more than a rule it states about the tree, and the only way to tell is to reintroduce the defect and look.

It earned that line the hard way. The header had recorded its own wrong-artefact rule as fixed, and two violations of it were live when somebody finally went and measured.

If you have a check standing between you and a class of bug, you already know it passes. Go and find out whether it fails.
